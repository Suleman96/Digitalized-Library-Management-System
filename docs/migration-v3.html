The call

The problem with the current build is not that it is written in Python — it is that the Python is writing HTML. recommender.py returns rendered book cards as strings. reading_list.py returns a rendered table. app.py holds 1,260 lines of CSS inside a Python string literal. No frontend of any language can be built on that, because there is no data layer to build on.

So the migration is a split, not a rewrite. The retrieval engine you built — hybrid BM25 + FAISS over a NetworkX knowledge graph, HyDE, multi-query RRF, cross-encoder re-ranking, a LangGraph ReAct agent across five LLM providers — stays in Python, because FAISS, sentence-transformers, and LangGraph have no honest JavaScript equivalent. It gets refactored to return JSON and served by FastAPI. A Next.js 15 + TypeScript app consumes that API and becomes the thing people actually see.

Net result for a reviewer landing on your GitHub: a typed monorepo, an OpenAPI contract, a live URL, and an ML backend that is now legible instead of buried in a 2,724-line UI file.

02 — The blocker, precisely

Here is the pattern that has to change, taken from the current code:

# recommender.py — the backend is a template engine
def _render_card(self, book: dict) -> str:
    return f'<div class="book-card"><img src="{book["thumbnail"]}">…'

# reading_list.py
def to_html(self) -> str: ...

# app.py — handlers return HTML strings straight into gr.HTML()
def _do_recommend(...) -> tuple[str, gr.update, list]: ...
def _load_reading_list() -> str: ...
def _concierge_ai_status() -> str: ...

Every one of these must return a Python object that serialises to JSON. Until that is true, the frontend language is irrelevant — React would just be receiving pre-rendered markup and dumping it through dangerouslySetInnerHTML, which is both an XSS surface and a pointless architecture.

The good news: the canonical book schema already exists. BookRecommender._normalise() at recommender.py:139 already produces exactly the flat dict a TypeScript type wants — title, authors, subtitle, description, thumbnail, average_rating, ratings_count, info_link, language, published_year, num_pages, source, similarity. The data model is sound. It is only the last mile that got templated.

The one schema change worth making

Books currently have no stable identifier — the UI selects them by title string, which breaks on duplicates and on any title containing punctuation. v3 adds a deterministic id (a hash of title + first author) so the frontend can key lists and route to /book/[id] properly.

Analytics needs the same treatment

_build_analytics() currently renders three Matplotlib PNGs server-side. In v3 it returns plain series data and the frontend draws them — which is faster, interactive, theme-aware, and removes Matplotlib from the server image entirely.

What deliberately does not carry over: the marketing site's hero proportions and CTA rhythm. A product needs to put controls and results above the fold.

The trace object is the differentiator

Right now the RAG pipeline's cleverness is invisible — a user searches and gets a list, with no evidence that HyDE ran, that three query variants were fused by RRF, or that a cross-encoder re-ordered the results. v3 returns a trace alongside every search:

type PipelineTrace = {
  originalQuery:   string
  expandedQuery?:  string        // llm.expand_query output
  hydeDocument?:   string        // the hypothetical doc that got embedded
  queryVariants?:  string[]      // the 3 multi-query rephrasings
  stages: Array<{
    name:      "bm25" | "faiss" | "graph" | "rrf" | "rerank"
    candidates: number
    durationMs: number
    topShift?:  number           // how far re-ranking moved things
  }>
  totalMs: number
}

The frontend renders this as a collapsible trace under the search bar. It costs one Pydantic model and one component, and it converts an invisible backend into the most demonstrable thing on the page.

08 — Deployment

Frontend · Vercel

Root apps/web. Push-to-deploy, preview URLs per branch, edge CDN, free tier. One env var: NEXT_PUBLIC_API_URL.

Backend · HF Spaces

Docker Space on the free CPU tier. Models cached in the image layer. Secrets set in Space settings, never in git.

Cost

$0per month, both tiers, indefinitely.

The cold-start problem, and the fix

HF free Spaces sleep after inactivity. A cold boot loads all-MiniLM-L6-v2, builds the FAISS index over ~6,800 books, fits BM25, and constructs the NetworkX graph — call it 30–45 seconds. A recruiter will not wait that out.

  • Pre-build the artifacts into the image. Commit or generate book_index.faiss and books_metadata.pkl at Docker build time rather than on boot. This is most of the win.
  • Cache the knowledge graph — hybrid_retriever.py already has _graph_cache_path(); make sure it lands in the image.
  • Pre-download the model in the Dockerfile so no HF fetch happens at runtime.
  • Warm it from the frontend. Fire /api/health from the root layout on first paint, and show an honest "waking the retrieval engine" state instead of a spinner that looks broken.
  • Optional: a GitHub Action pinging /api/health every 30 minutes keeps it warm for free.

Do not ship your API keys to a public demo. The app supports five providers. For the public deployment, expose Groq (free tier, fast) as the default, rate-limit it per IP, and let visitors paste their own key for Claude or OpenAI. Never commit a key, and rotate anything that has ever been in .env before this repo goes fully public.

09 — Making it reviewable

You want people to land on this and understand the system. That is a design problem, and it does not solve itself by having good code.

The /how-it-works page

You already have this content — it is spread across docs/ARCHITECTURE_V2.md, three standalone HTML files, and two PDFs. In v3 it becomes a page in the app, at a URL, with the real system running underneath it: an interactive walkthrough where a visitor types a query and watches HyDE generate a hypothetical document, sees the three query variants, sees BM25 and FAISS candidate sets side by side, and sees the cross-encoder reorder them. Same data as the trace component, presented pedagogically.

This is the single highest-return thing on the list. It is the difference between "another book search app" and "someone who can explain retrieval architecture to a client."

10 — Risks and mitigations

RiskWhy it bitesMitigation
Cold starts read as "broken" Free-tier sleep plus a 30s index build is the most likely reason a reviewer bounces Bake artifacts into the image; warm on first paint; honest loading copy; optional keep-alive cron
Public LLM key abuse An open endpoint calling Claude on your key is an uncapped bill Groq free tier as public default, per-IP rate limit, bring-your-own-key for premium providers
P0 scope creep Removing HTML rendering touches every test; it is tempting to "improve while in there" P0 is deletion and shape-change only. No new features until P1 is green
Type drift between API and web Hand-written TS interfaces silently diverge from Pydantic models Generate lib/types.ts from OpenAPI; run gen:types in CI and fail on diff
HF Spaces memory ceiling Free tier is 16 GB but CPU-only; the cross-encoder plus MiniLM plus FAISS plus 6,800 rows is fine, a larger corpus may not be Lazy-load the re-ranker (already the case), monitor at /api/health, cap corpus growth
Losing working behaviour in translation Gradio handlers contain accumulated edge-case handling that is easy to drop Keep app.py in the tree until P6; diff behaviour side-by-side before deleting it
SSE through the Space proxy Streaming can buffer behind some proxy configurations Disable response buffering explicitly; fall back to a non-streaming POST if the stream fails to open
