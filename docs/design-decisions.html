01
Vector Search: FAISS IndexFlatIP
Retrieval

Chosen: FAISS IndexFlatIP current

Why: At 6,810 books with 384-dim vectors, the full index is ~10MB in RAM. IndexFlatIP performs exact inner-product search in milliseconds with zero configuration. It requires no training, no approximation parameters to tune, and outputs deterministic results. When the corpus is this small, the speed advantage of approximate methods (HNSW, IVF) is negligible while their added complexity and recall trade-offs are real.

Alternatives Considered

FAISS IndexHNSW
✗ Overkill for now

Approximate search, ~5% recall loss, but 10× faster at 1M+ vectors. Worth switching if corpus grows beyond 200k books.

FAISS IndexIVFFlat
✗ Not needed yet

Requires training on representative vectors. Faster than Flat at large scale but adds complexity. Use at 500k+ books.

ChromaDB
⚠ Consider for HuggingFace Spaces

Persistent vector DB with metadata filtering built in. Survives cold starts without rebuilding. Trade-off: requires a server process.

Qdrant
✗ Too heavy

Production-grade vector DB. Excellent for millions of vectors with payload filtering. Significant overhead for 6.8k books.

Annoy
✗ Inferior

Memory-mapped approximate search. Read-only after build (no incremental adds). FAISS is strictly better.

pgvector
⚠ Consider if adding Postgres

Vector extension for PostgreSQL. Ideal if you want metadata filtering + vector search in one SQL query.

How to improve: When corpus exceeds 100k books, switch to IndexHNSWFlat (keep recall >99% with ef_search=128). For production deployments, replace with ChromaDB to avoid index rebuilds on server restarts.
02
Keyword Search: BM25 via rank_bm25
Retrieval

Chosen: rank_bm25 (BM25Okapi) current

Why: FAISS alone misses exact-match queries — author names, ISBNs, specific title words. BM25 is the gold standard for keyword retrieval (it powers Elasticsearch). The rank_bm25 library is pure Python, no server needed, and integrates in ~5 lines. BM25Okapi specifically handles term frequency saturation better than basic TF-IDF.

Alternatives Considered

Elasticsearch / OpenSearch
✗ Too heavy

Best-in-class keyword search with typo tolerance, stemming, and faceting. Way too heavy to run embedded in a Python app for 6.8k books.

Whoosh
✗ Unmaintained

Pure-Python inverted index. Last major update 2016. rank_bm25 is simpler and more actively maintained.

Typesense
⚠ Future option

Open-source search engine with typo tolerance, fast BM25, and REST API. Excellent alternative if deploying as a service.

TF-IDF (sklearn)
✗ Inferior to BM25

Classic but doesn't handle term frequency saturation — a word appearing 100× gets 100× the weight. BM25Okapi caps this correctly.

How to improve: Add stemming (e.g. nltk.stem.PorterStemmer) so "mysteries" matches "mystery". Add stopword filtering ("a", "the", "of") to reduce noise in BM25 scores. For Arabic books, add Arabic stemming via nltk.stem.isri.
03
Hybrid Fusion: Custom Implementation vs LangChain
Retrieval

Chosen: Custom BM25 + FAISS fusion (no LangChain) current

Why: LangChain 1.3.1 (the installed version) silently removed EnsembleRetriever from both langchain and langchain-community. The original v2 plan used it, but it failed at runtime. Rather than pin to an older LangChain version (which breaks the agent), we implemented hybrid fusion directly with rank_bm25 and raw FAISS — removing the framework dependency entirely. The result is simpler, faster, and doesn't break with LangChain upgrades.

Alternatives Considered

LangChain EnsembleRetriever
✗ Removed in v1.3.1

Was the original plan. API was removed in LangChain 1.3.1 without a clear migration path. Using it would require pinning LangChain to a version incompatible with the agent.

Weaviate (native hybrid)
⚠ Future option

Has BM25+vector hybrid built into the database. Ideal if replacing FAISS+CSV with a proper vector DB. Adds a server dependency.

LlamaIndex HybridRetriever
✗ Framework lock-in

Similar approach but ties the codebase to a second large framework alongside LangChain. Custom implementation avoids this.

How to improve: The current RRF implementation in rag_pipeline.py handles multi-query fusion. For single-query hybrid fusion in hybrid_retriever.py, consider replacing min-max normalisation with learned weights trained on user click data — when available.
04
Fusion Weights: 40% BM25 / 60% FAISS
Retrieval

Chosen: Fixed 40/60 weighting with min-max normalisation current

Why: Semantic understanding (FAISS) is more valuable than keyword overlap for book discovery — users rarely know exact titles. 60/40 was chosen empirically by testing against known good results. Min-max normalisation is applied separately to each score vector so the two scales don't interact: a BM25 score of 500 doesn't overwhelm a FAISS score of 0.8 just because it's numerically larger.

Alternatives Considered

50% / 50% equal weighting
✗ Tested, worse

Equal weighting was tested but keywords dominated for short queries and FAISS dominated for long ones in undesirable ways. 40/60 produced more consistent results.

Learned weights (LTR)
✓ Best long-term

Learning-to-rank using click data / user feedback. Weights adapt per query type. Would require collecting interaction logs first.

Query-type adaptive
⚠ Moderate win

Short queries (<3 words) → higher BM25 weight. Long natural language queries → higher FAISS weight. Rule-based, implementable without ML.

How to improve: Implement query-length adaptive weights: if len(query.split()) < 3, use 60% BM25 / 40% FAISS (keywords likely intentional). For queries with 4+ words, use 30% BM25 / 70% FAISS (natural language intent).
05
Pre-retrieval: HyDE (Hypothetical Document Embeddings)
AI

Chosen: LLM generates hypothetical book description; embed that current

Why: Embedding a user query like "something uplifting about grief" produces a vector in "query space" which doesn't perfectly overlap with "book description space" even though both use the same model. HyDE bridges this gap: the LLM writes a fake 2-sentence book description matching the intent, and that text embeds much closer to actual book descriptions in FAISS. This is especially effective for abstract or emotional queries.

Alternatives Considered

Average HyDE + original query
⚠ Better than HyDE alone

Average the embedding of the hypothetical doc with the original query embedding. Reduces risk of LLM hallucinating in the wrong direction. Low additional cost.

Query2Doc
⚠ Similar approach

Generate a short document summarising what a good answer would contain, then prepend it to the query. Similar idea, slightly different implementation.

Step-back prompting
✗ Less effective here

LLM generates a more abstract version of the query. Helps in QA tasks but less useful for book discovery where we want MORE specificity, not less.

Pseudo-relevance feedback (PRF)
✗ No LLM needed but weaker

Take top-k results from first pass, extract keywords, re-query. Classic NLP technique but requires a first search pass and is less intelligent than HyDE.

How to improve: Average the HyDE embedding with the original query embedding (weighted 70% HyDE / 30% original). This keeps the directional improvement of HyDE while preventing extreme drift when the LLM hallucinates an irrelevant direction. Code change: 
q_vec = 0.7 * embed(hypo_doc) + 0.3 * embed(query)
q_vec /= np.linalg.norm(q_vec)  # re-normalise

Pre-retrieval: Multi-Query + Reciprocal Rank Fusion
AI

Chosen: LLM generates 3 variants; merge with RRF (k=60) current

Why: A single query phrasing often misses books that would have been found with a different wording. "Hacking stories" might miss "cybersecurity thrillers" and vice versa. By running 3 LLM-generated variants through the retriever and merging with RRF, we dramatically increase recall without increasing the final result count. RRF was chosen over score averaging because it's rank-based (not score-based) — it works regardless of whether BM25 and FAISS use different score scales.

RRF Formula

score(doc) = Σ  1 / (rank_in_list_i + 60)
             i∈lists

# The constant 60 controls how steeply rank matters.
# Higher → gentler (position 1 vs 2 matters less).
# 60 is the standard from the original 2009 paper.

Alternatives Considered

Score averaging
✗ Scale-sensitive

Average the similarity scores across queries. Breaks when queries have different score distributions (BM25 scores are unbounded, FAISS is [0,1]).

Simple deduplication
⚠ Much simpler

Collect all results from all queries, deduplicate by title, keep original scores. Loses the rank-boosting effect of RRF. Good fallback if performance is a concern.

Synonym expansion (no LLM)
✗ Less powerful

Use a thesaurus/WordNet to expand query terms. Free (no LLM call) but misses contextual variants and domain-specific synonyms that the LLM generates well.

5 variants instead of 3
⚠ Marginal gain

More variants = more coverage. Diminishing returns after 3-4 variants. Each adds one retriever call. Good for high-stakes searches.

How to improve: Cache query variant generations per session — if the user searches the same query twice, reuse the variants. Use functools.lru_cache or a simple dict keyed by the query string. This eliminates redundant LLM calls on re-searches.
07
Post-retrieval: Cross-Encoder Re-ranking
Ranking

Chosen: cross-encoder/ms-marco-MiniLM-L-6-v2 current

Why: Bi-encoders (like our FAISS embedder) encode query and document independently, then compare. Cross-encoders see the query and document together in one forward pass, allowing the model to attend to interactions between them — producing much more accurate relevance scores. ms-marco-MiniLM-L-6-v2 is small (~70MB), fast, and trained specifically on relevance ranking tasks (MS MARCO passage ranking dataset).

Alternatives Considered

Cohere Rerank API
✓ Best quality, costs money

State-of-the-art re-ranking via API. No local model to maintain. ~$1 per 1000 reranked results. Excellent for production where quality justifies cost.

ms-marco-MiniLM-L-12-v2
⚠ Better quality, slower

12-layer version of the same model. ~15% better ranking accuracy, ~2× slower. Worth switching if GPU is used for inference.

bge-reranker-base
⚠ Strong alternative

BAAI's re-ranker. Strong multilingual performance — better for Arabic books. Same size as ms-marco-MiniLM.

GPT-4o as re-ranker
✓ Highest quality (expensive)

Ask GPT-4o to rank a list of books for the query. Understands nuance, context, and themes better than any small model. Expensive at scale.

monoBERT
✗ Too slow

BERT-based cross-encoder, the original. Good quality but 3× slower than MiniLM with similar accuracy. Not worth it.

How to improve: The cross-encoder currently loads on first use (~3s). Pre-load it at startup in a background thread so the first re-rank request is instant. Also: run inference on the RTX 3060 GPU by passing device="cuda" to CrossEncoder() — this drops re-ranking latency from ~300ms to ~30ms. 
from sentence_transformers import CrossEncoder
self._reranker = CrossEncoder(
    "cross-encoder/ms-marco-MiniLM-L-6-v2",
    device="cuda"  # use GPU if available
)
08
Embedding Model: all-MiniLM-L6-v2
AI

Chosen: sentence-transformers/all-MiniLM-L6-v2 (22MB, 384-dim) current

Why: The best balance of size, speed, and quality for English book search. 22MB means it loads in <1s and fits in RAM alongside the application. 384 dimensions keep the FAISS index small (~10MB for 6.8k books). Trained on 1 billion sentence pairs — strong semantic understanding despite the small size.

Alternatives Considered

BAAI/bge-small-en-v1.5
⚠ Slightly better quality

Same size, similar speed, consistently outperforms all-MiniLM on BEIR benchmark. Drop-in replacement worth considering.

BAAI/bge-m3
⚠ Best for multilingual

Supports 100+ languages including Arabic. 570MB model, 1024-dim. The right choice when Arabic book support becomes important.

text-embedding-3-small (OpenAI)
✗ API cost + latency

Excellent quality. But requires API call per embedding — adds latency and cost for every search and every book added to the catalogue.

all-mpnet-base-v2
✗ Too heavy

Higher quality than MiniLM but 420MB, 768-dim. Index doubles in size, load time increases. Not worth it at this scale.

How to improve: Switch to BAAI/bge-small-en-v1.5 for a quality improvement with zero size penalty. For Arabic and multilingual support, plan a migration to BAAI/bge-m3 — but note this requires rebuilding the FAISS index (dimensions change from 384 to 1024, and all existing embeddings must be regenerated).

Agent Framework: LangGraph ReAct
AI

Chosen: LangGraph create_react_agent + MemorySaver current

Why: The conversational librarian needs: (1) tool use — calling search functions as needed, (2) conversation memory — remembering "the book I mentioned earlier", (3) multi-turn reasoning — planning multi-step actions. LangGraph provides all three via a stateful graph with checkpointing. It also integrates natively with all four LLM providers (Claude, OpenAI, Gemini, Ollama) via LangChain chat models.

Alternatives Considered

Simple chat loop
✗ No tool use

Pass the full conversation history to the LLM each turn. Fast and simple, but can't call search functions — the librarian would be limited to what's in its training data.

AutoGen
✗ Multi-agent overkill

Designed for multi-agent conversations between AI models. Unnecessary complexity for a single-agent tool-using assistant.

CrewAI
⚠ Simpler syntax

Higher-level abstraction over LangChain agents. Easier to set up but less control over the graph structure and state management.

Claude's native tool use
✓ Best for Claude-only

Anthropic's tool use API is excellent. If the project commits to Claude as the only provider, native tool use would be simpler than LangGraph + LangChain adapters.

How to improve: Add streaming output so responses appear word-by-word instead of all at once. In Gradio, use gr.ChatInterface's streaming mode with a generator function. Also add a tool call indicator so users see "🔍 Searching local library..." while the agent is working.

Multi-Provider LLM Abstraction
AI

Chosen: Custom LLMProvider class supporting 4 backends current

Why: Locking into one AI provider creates cost and availability risk. If Anthropic has an outage or raises prices, the whole system fails. Supporting Claude, OpenAI, Gemini, and Ollama lets users choose: free and local (Ollama), most capable (Claude), or cost-optimized (GPT-4o-mini). The custom abstraction means no framework dependency — just direct API calls.

Alternatives Considered

LiteLLM
✓ Best long-term

Unified interface to 100+ LLM providers. Drop-in replacement for OpenAI API. Would replace our custom LLMProvider with one well-maintained library. Recommended for v3.

Single provider (Claude only)
✗ Vendor lock-in

Simpler code. But creates hard dependency on Anthropic — users without API keys get no AI at all. Ollama support is especially important for offline/cost-free use.

LangChain as LLM layer
⚠ Already partially used

Use LangChain's chat model abstractions everywhere (not just the agent). Consistent but adds another layer of abstraction and LangChain version sensitivity.

How to improve: Replace the custom LLMProvider with LiteLLM. One library handles all providers, model aliases, fallbacks, cost tracking, and token counting. Reduces maintenance burden significantly. 
import litellm
response = litellm.completion(
    model="claude-sonnet-4-6",
    messages=[{"role": "user", "content": prompt}]
)

UI Framework: Gradio
Framework

Chosen: Gradio 4.x current

Why: For an AI/ML prototype, Gradio is the fastest path from Python functions to a working web UI — no JavaScript knowledge required. It handles state management, file uploads/downloads, chatbots, and plots natively. First-class support for HuggingFace Spaces deployment (our next deployment target).

Alternatives Considered

Streamlit
⚠ Simpler but less flexible

Even faster to prototype. But re-runs the entire script on every interaction, making state management complex. Less suitable for chat interfaces.

FastAPI + React
✓ Best for production

Proper separation of backend API and frontend. Full control over UX. Required for mobile responsiveness, PWA, and integrating into existing websites. Significant development time.

Dash (Plotly)
✗ Charts only

Excellent for data dashboards. But not designed for chat interfaces or AI workflows — would require significant workarounds.

Chainlit
⚠ Better for chat-focused apps

Specifically designed for LLM chat interfaces. Has streaming, tool call visualization, and authentication built in. Worth considering if the librarian chat is the primary UX.

How to improve: Keep Gradio for the prototype and HuggingFace Spaces deployment. For a production website, build a FastAPI backend (keep all current Python modules as-is) and a React/Next.js frontend that calls the API. The current architecture already supports this — each module is independent and testable.
12
Storage: CSV + Pickle + JSON
Storage

Chosen: CSV (catalogue) + Pickle (metadata) + JSON (reading list) current

Why: Three formats serve three distinct purposes. CSV is human-readable and editable in Excel — important for a library admin. Pickle stores the pre-processed metadata list parallel to FAISS row indices (fast to load, preserves Python types). JSON for the reading list is simple, human-readable, and personal (git-ignored).

Alternatives Considered

SQLite
⚠ Better at scale

Single file database. Better querying (filter by author, year, rating). Atomic writes. Ideal when catalogue grows beyond 50k books or reading list needs queries.

PostgreSQL + pgvector
✗ Overkill for local deployment

Combines relational storage + vector search in one system. Excellent for multi-user production deployments. Heavy for a single-user local app.

Parquet instead of CSV
✗ Not human-readable

10× faster reads, columnar compression. But not editable in Excel — breaks the "library admin" use case.

How to improve: Replace the CSV + Pickle combination with a single SQLite database (books.db) using Python's built-in sqlite3. Keep FAISS for vector search but store all metadata in SQLite — enabling filter-before-search (e.g. "find similar books, but only published after 2010 in Arabic").

Improvement Roadmap
Roadmap

Prioritised by impact vs effort. High = quick win. Low = long-term investment.

  • High
    GPU cross-encoder: Pass device="cuda" to CrossEncoder — drops re-ranking from 300ms to 30ms on RTX 3060. One-line change.
  • High
    bge-small-en-v1.5 embedder: Drop-in replacement for all-MiniLM-L6-v2. Better BEIR benchmark scores, same size. Requires FAISS index rebuild.
  • High
    HyDE embedding average: Blend HyDE doc embedding (70%) with original query (30%). Prevents hallucination drift with minimal code change.
  • High
    BM25 stemming: Add nltk.stem.PorterStemmer to corpus tokenisation. "mysteries" → "mysteri" matches "mystery". Install: pip install nltk.
  • Med
    Query-length adaptive weights: Short queries → higher BM25 weight. Long queries → higher FAISS weight. ~15 lines of code in hybrid_retriever.py.
  • Med
    Agent streaming output: Stream responses word-by-word via Gradio generator. Much better UX than waiting 3s for a full response.
  • Med
    Query variant caching: Cache LLM query variants per session to avoid redundant API calls on re-searches. Simple dict in rag_pipeline.py.
  • Med
    bge-reranker-base: Replace ms-marco cross-encoder with BAAI's reranker for better multilingual (Arabic) support.
  • Med
    SQLite migration: Replace CSV + Pickle with SQLite. Enables filter-before-search and atomic writes without FAISS rebuild.
  • Low
    LiteLLM backend: Replace custom LLMProvider with LiteLLM for 100+ provider support, cost tracking, and automatic fallbacks.
  • Low
    bge-m3 embedder: Switch to multilingual model for Arabic and 100+ language book support. Requires full FAISS index rebuild, 570MB model.
  • Low
    HNSW index: Switch to IndexHNSWFlat when corpus exceeds 200k books. Configure ef_construction=200, ef_search=128 for >99% recall.
  • Low
    FastAPI + React frontend: Production-grade deployment with mobile support, authentication, and API for third-party integrations.
